When you just can't bother with ImageMagick

The following project is a backend implementation of an online image conversion service. Utilizing Spring Boot, Spring Security, PostgreSQL and Cloudflare's R2, it offers a solid foundation for helping users convert their personal images at scale.

For higher throughput, conversions are done concurrently by the server. Multiple workers are continuously scheduled and query submitted conversion tasks directly from the database, which acts as the task queue (see Concurrency).

Users need an account to access the service and can optionally acquire a product key to upgrade their account to premium for unlimited conversions each week. The whole user ecosystem is secured via Spring Security.

Image storage is handled exclusively by Cloudflare's R2 object storage service (S3-compliant). It is the intermediary between the client and the backend workers.

Concurrency: Converting multiple images at once

At the heart of the project is a group of concurrently running conversion workers. These workers are handled by a ThreadPoolTaskScheduler and get continuously rescheduled, with a back-off delay if the queue has run dry.

Postgres plays a vital part in my approach to concurrency, with the task table acting as a queue for the workers. This is where Postgres truly shines with the following magical syntax: 

FOR UPDATE SKIP LOCKED

Four words that prevent

  • Duplicate processing
  • Deadlocks
  • Getting stalled by locked rows (compared to plain FOR UPDATE)

The first part FOR UPDATE ensures rows returned by SELECT are locked for modification (incl. further locking) for the duration of the transaction. However, because FOR UPDATE is a locker itself, it gets stalled by locked row matches. The exact opposite of what we want for concurrent access. FOR UPDATE SKIP LOCKED sidesteps this issue by ignoring locked rows entirely as if they don't exist.

This way the database both locks tasks to prevent double claims, but also continues to provide immediate access for new worker queries.
